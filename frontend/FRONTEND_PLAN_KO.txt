현재 프로젝트는 회원 관리, 소속 대학 수동 인증, 러닝 계산·저장·조회, 대학 합산·평균·순위, 비정상 판정을 제공하는 C 백엔드와 브라우저 GPS 측정 모듈까지 준비돼 있다. 두 코드는 같은 기능 브랜치에 모여 있고, 가상 GPS로 수집한 좌표를 실제 서버에 보내 저장하고 다시 조회하는 테스트도 했다. 다만 일반 사용자가 화면에서 러닝을 시작하고 종료한 뒤 자동 저장하는 앱 연결 코드는 아직 없다. 관리자 사진 검토 화면은 일반 회원용 앱 화면을 대신하지 않는다. 2026년 11월 2일에는 저장 완료 뒤 정리 함수를 호출하면 임시 기록이 다시 생기던 오류를 수정했고, 미저장 기록의 복구는 유지하도록 보완했다.

남아 있는 핵심 구현은 회원용 메인·러닝·기록·대학 순위·내 정보 화면과 화면 이동, 지도에 실시간 및 과거 경로를 그리는 기능, GPS 종료 결과를 서버에 저장하는 연결 서비스, 실패한 저장을 같은 요청으로 재시도하는 처리, 개인 기록의 주간·월간 변화 그래프다. 가입·로그인·학교 선택·서류 제출·처리 결과·탈퇴·비밀번호 변경도 서버 API는 있지만 일반 회원 화면에서 호출하도록 연결해야 한다. 실제 휴대폰이 접근할 HTTPS 주소와 허용 Origin을 준비하고, GPS 권한 거부·수신 단절·화면 꺼짐·통신 실패를 실기기에서 확인하는 작업도 남아 있다. 이메일 기반 비밀번호 분실 복구와 운영자별 독립 계정은 별도 추가 범위이며 현재 구현돼 있지 않다. 학교를 고르는 것과 소속 인증이 승인되는 것은 다르고, 승인이 끝난 회원의 정상 기록만 대학 점수에 반영된다는 점을 화면에서도 알려야 한다.

프런트의 틀을 먼저 맞추자는 것은 필요한 협의다. 다만 모든 디자인을 완성할 때까지 기다릴 필요는 없고, 사용할 도구, 화면 구성, 화면 이동 방식, 모듈의 입력과 출력, 공통 단위만 먼저 확정하면 각자 병렬로 시작할 수 있다. 현재 저장소에는 프런트 프레임워크나 package.json이 없고 GPS 모듈과 API 클라이언트가 JavaScript 모듈로 작성돼 있으므로, 아직 팀 합의가 없다면 Vite의 vanilla JavaScript 템플릿과 일반 CSS를 기본안으로 제안한다. 기존 모듈을 그대로 사용하고 개발 서버와 배포 빌드만 Vite로 관리하는 구성이다. 팀이 이미 React 등으로 합의했다면 그 결정을 확인한 뒤 같은 데이터와 역할 구분을 적용하면 된다. 이번 제안은 틀에 대한 문서이며 프로젝트 생성, 의존성 설치, 새 UI 코드는 작성하지 않았다. Vite의 공식 안내는 https://vite.dev/guide/ 이다.

화면은 하나의 HTML 진입점에서 내용만 전환하는 모바일 웹 구조로 잡고, 첫 버전은 해시 기반 화면 이동으로 구성하면 된다. 하단 메뉴는 홈, 러닝, 기록, 대학, 내 정보로 통일한다. 홈은 개인 누적 거리와 내 대학 성적, 러닝 시작 버튼을 보여준다. 러닝은 위치 수신 상태, 거리, 운동 시간과 시작·종료 버튼을 중심으로 구성한다. 기록은 과거 목록과 기간별 변화 그래프를 보여주고, 항목을 누르면 상세 결과와 지도 경로를 보여준다. 대학은 동일한 조회 기간의 전체 순위와 내 대학 성적을 함께 표시한다. 내 정보에서는 계정, 소속 대학, 인증 상태, 서류 제출, 비밀번호 변경, 로그아웃과 탈퇴로 이동한다. 로그인·가입·서류 제출·기록 상세는 이 기본 화면에 딸린 세부 화면으로 두고 운영자 검토 화면은 현재 예제를 별도 화면으로 유지한다.

화면 코드, 공통 UI, 상태 관리, GPS, 서버 통신, 기록 저장·분석, 지도 기능은 역할을 구분한다. GPS 담당은 현재 RunTracker를 관리하고 위치·시간·거리와 좌표를 제공한다. 기록 담당은 종료된 좌표와 한 번 만든 제출 식별자를 보관하고 서버 저장·재시도·목록 조회·기간별 분석을 담당한다. 프런트 담당은 공통 화면과 이동 구조를 만들고 이 모듈들의 결과를 표시한다. 회원·대학 담당은 회원·서류·대학 성적 API 연결과 데이터 규칙을 담당하며 프런트 담당의 공통 컴포넌트를 재사용한다. 좌표를 수집하는 코드나 로그인 토큰을 관리하는 API 클라이언트를 화면마다 따로 만들지 않는다. 실행 중인 GPS 객체와 로그인 상태는 앱 공통으로 유지하고, 화면에서는 구독과 구독 해제만 한다. 러닝 화면을 벗어났다는 이유만으로 dispose()를 호출해 측정을 끝내면 안 되며, 종료 또는 사용자에게 확인받은 이탈 때 정리해야 한다.

화면이 바뀌어도 앱의 공통 상태에는 로그인한 회원, 소속과 인증 상태, 진행 중인 러닝, 저장 중인지 실패했는지, 선택한 기록과 조회 기간이 유지돼야 한다. 위치를 받는 중, 러닝 중, 종료, 저장 중, 저장 완료와 저장 실패를 구분하고 상태에 맞춰 버튼을 활성화한다. 기록 담당의 저장 서비스는 종료된 좌표를 서버에 전달하고 성공이 확인된 뒤에만 markSaved()로 임시본을 정리한다. 실패나 응답 유실 때는 식별자와 좌표를 바꾸지 않고 그대로 재시도한다. 현재 API 클라이언트의 회원 토큰은 메모리에 있으며 새로고침 후 재로그인이 필요하다는 동작도 화면에서 일관되게 처리한다. 관리자 토큰을 회원 화면이나 번들에 넣지 않는다.

팀 공통 규격은 현재 API를 그대로 따른다. GPS는 timestamp, latitude, longitude를 제공하고 timestamp는 밀리초가 아닌 UTC 정수 초로 정리한다. 같은 초의 좌표는 중복되지 않게 처리하고, 서버가 받지 않는 accuracy나 임의의 회원 ID·거리 값을 저장 본문에 추가하지 않는다. 서버의 거리는 미터, 시간은 초, 속도는 m/s, 페이스는 초/km이며 화면에서만 km·km/h·분:초로 바꾼다. 러닝 중 숫자는 미리보기이고 저장 후에는 서버 계산 결과를 최종 기록으로 표시한다. 현재 서버의 운동 시간은 첫 유효 좌표부터 마지막 유효 좌표까지이므로 버튼을 누른 시각이나 일시정지 시간을 별도 운동 시간으로 쓰려면 먼저 API 합의가 필요하다. accepted는 GPS 판정이고 counts_for_university는 학교 인증까지 포함한 대학 점수 반영 여부라는 차이도 유지한다.

지도는 GPS를 다시 측정하지 않고 현재 좌표 배열이나 기록 상세 API의 points를 받아 경로선을 그리는 공통 모듈로 만든다. 시작점과 끝점, 현재 위치와 경로 전체 보기를 공통으로 지원하되 지도 공급자와 필요한 키·이용 조건은 구현 전에 팀에서 하나로 정한다. 기록의 변화 그래프는 기존 기간 합산 API로 이번 주와 지난주를 비교하는 것부터 시작하고, 일별 그래프가 필요하면 목록을 페이지 끝까지 조회해 날짜별로 묶거나 백엔드 담당과 집계 API를 확장한다. 전체 평균 속도와 페이스는 총 거리와 총 시간으로 계산하고 러닝별 평균을 단순 평균하지 않는다. 날짜 기준은 한국 시간으로 맞추고 이전 기간이 0이거나 기록이 없는 경우도 별도로 표시한다.

디자인은 모바일 세로 360~430px 폭을 먼저 기준으로 잡고, PC에서는 앱 영역의 최대 폭을 정해 중앙에 배치한다. 밝은 배경에 짙은 글자와 한 가지 강조색을 쓰고 카드, 입력창, 버튼, 오류 안내와 여백 규칙을 공통으로 맞춘다. 러닝 시작·종료와 저장 실패 재시도처럼 중요한 동작은 화면에서 분명하게 보여야 하고, 하단 메뉴가 주요 버튼이나 지도를 가리지 않도록 한다. 빈 기록, 로딩, 위치 권한 거부, 인증 대기와 저장 실패 화면까지 틀에 포함하면 기능 담당이 각자 임의의 경고창과 화면을 만들지 않아도 된다.

첫 목표는 화면 전체의 완성도가 아니라 로그인하고 러닝을 시작해 좌표를 모은 뒤 종료·저장하고 기록 상세와 지도에서 다시 확인하는 흐름이다. 프런트 담당은 예제 데이터로 화면과 이동을 먼저 만들 수 있고, GPS 담당은 현재 모듈을 유지하며, 기록 담당은 이미 있는 API로 저장과 조회를 연결할 수 있다. 이 흐름이 되면 사진 승인 뒤 대학 점수와 순위가 바뀌는 것을 연결하고 마지막에 기간 분석과 스타일을 다듬으면 된다. 각자 만든 모듈의 입력·출력과 담당 파일을 공유하고 실제 연결 시연을 기준으로 완료를 판단하면, 누군가의 디자인 결정 때문에 다른 작업이 모두 멈추는 상황을 줄일 수 있다.
